# Тестовое задание: PHP Backend Developer (Laravel)

## О задании

Это тестовое задание оценивает вашу способность работать с Laravel, писать чистый и безопасный код, и анализировать код других разработчиков.

**Время:** 3–4 часа
**Вакансия:** PHP Backend Developer (Laravel)

### Что мы оцениваем

- Дисциплина валидации данных и написание защищённого кода
- Тестирование (feature-тесты, правильная структура)
- Понимание чистоты слоёв (модель ≠ контроллер)
- Чтение и анализ "чужого" кода (код-ревью)
- Осознанность в работе с БД (производительность запросов, целостность данных)
- Использование ИИ: честность, вспомогательная роль, не замена думанию

## Setup

### Требования

- PHP 8.2+
- Composer
- SQLite (встроено в PHP)

### Шаги

```bash
# 1. Распаковываем архив и переходим в проект
unzip hiring-test-php-laravel.zip
cd hiring-test-php-laravel

# 2. Устанавливаем зависимости
composer install

# 3. Копируем .env и генерируем ключ
cp .env.example .env
php artisan key:generate

# 4. Создаём БД и заполняем данными

php artisan migrate --seed

# 5. Проверяем, что baseline работает
php artisan test

# 6. Запускаем сервер (опционально)
php artisan serve
```

## Блок А: Расширить приложение (M:M Post ↔ Tag)

Стартовый проект содержит **baseline-код** для работы с постами (`Post`, `PostController`). Также в baseline уже есть пустая модель `Tag` и таблица `tags` (поля `name`, `slug`) — чтобы ты не тратил время на тривиальный boilerplate. Твоя задача — связать теги с постами и дать API.

### Что нужно сделать

Реализуй связь «многие-ко-многим» между постами и тегами и API для управления ею. Требования:

1. **Связь Post ↔ Tag** — «многие-ко-многим»: у поста может быть несколько тегов, у тега — несколько постов. Модель `Tag` и таблица `tags` уже есть; всё остальное для связи (в т.ч. хранилище связи) — на тебе.

2. **Два API-эндпоинта**:
   - привязать один или несколько тегов к посту;
   - отвязать тег от поста.

   URL и HTTP-методы выбери сам по конвенциям REST.

3. **Валидация входных данных** — запрос на привязку должен принимать список идентификаторов тегов; каждый идентификатор обязан ссылаться на существующий тег, иначе — ошибка валидации. Способ валидации — на твоё усмотрение (но см. критерии ниже).

4. **Теги в ответе API** — представление поста должно уметь отдавать связанные с ним теги.

5. **Feature-тесты** (минимум 3), покрывающие: привязку тегов, отвязку тега, чтение поста с тегами.

Готовый код мы не даём намеренно — задача в том, чтобы ты сам выбрал инструменты Laravel и написал реализацию.

### Опциональное расширение (не обязательно)

Полный CRUD для `/tags` (index/store/update/destroy). Приветствуется, но не требуется для базовой оценки.

### На что смотрим в Блоке А

✅ **Валидация** — вынесена из контроллера, невалидный ввод отклоняется до записи в БД (какой инструмент — твой выбор)
✅ **Тесты** — feature-тесты, изоляция БД между тестами
✅ **Чистые слои** — контроллер тонкий, логика не размазана по нему
✅ **Безопасность** — нет Mass Assignment уязвимостей

## Блок Б: Код-ревью (`PublishController`)

В проекте находится файл `app/Http/Controllers/PublishController.php` — **намеренно "грязный" код** как пример дурной практики.

### Что делать

**Файл НЕ редактировать — только читать.**

1. Внимательно изучи `PublishController`.
2. Найди проблемы. Сколько их — определи сам; здесь есть что найти на нескольких уровнях (безопасность, производительность, архитектура, целостность данных).
3. Опиши каждую:
   - Что проблемно?
   - Какие последствия?
   - Как бы ты её исправил?

Ответ напиши в файл `REVIEW.md` (создай его в корне проекта). Формат ответа — по одному блоку на проблему. Ниже — пример **формата** на постороннем коде (не из этого проекта), чтобы показать структуру, а не подсказать ответ:

```markdown
# Разбор PublishController

## Проблема 1: <короткое название>

**Где:** Метод `foo()`, примерно строки 12–18.

**В чём суть:** Метод возвращает список сущностей без пагинации, поэтому на большой таблице ответ вырастает неограниченно.

**Последствие:** Рост потребления памяти и времени ответа пропорционально размеру таблицы; риск таймаута на проде.

**Исправление:** Добавить постраничную выборку (`paginate()`) и отдавать метаданные страницы.

## Проблема 2: <...>
...и так по каждой найденной проблеме.
```

### На что смотрим в Блоке Б

✅ **Самостоятельное думание** — ты сам называешь проблемы и обосновываешь их
✅ **Полнота** — найдены существенные проблемы разного уровня, а не одна-две очевидных
✅ **Осознанность** — объясняешь "почему" проблемно, не просто "это плохо"

## ИИ в обоих блоках

**Разрешено использовать ИИ**, но честно:

1. **ИИ в Блоке А** — помощник при написании кода:
   - Генерация boilerplate (migration, model, request)
   - Подсказки по валидации и RelationShip
   - Помощь при написании тестов
   
   ✅ Принимается: «Попросил ИИ сгенерировать миграцию, потом доработал сам»
   ❌ Не принимается: «Скопировал весь код целиком»

2. **ИИ в Блоке Б** — помощник при поиске проблем:
   - ИИ может указать на потенциальные проблемы
   - Твоё слово — что реально проблемно и почему
   
   ✅ Принимается: «ИИ указал, куда посмотреть, — вот мой собственный разбор проблемы»
   ❌ Не принимается: «ИИ сказал, я переписал его ответ»

**Обязательно приложи лог использования ИИ.** Два способа на выбор:

- **(A)** заполнить `AI-LOG.md` — короткое описание своими словами (что просил, что принял / отклонил / доработал); или
- **(B)** приложить сырой лог сессии из своего инструмента (Claude Code / ChatGPT-share / Cursor history и т.п.) — файлом в репозитории или ссылкой в `AI-LOG.md`.

Если выбираешь (B) — добавь сверху 2–3 строки: где ИИ был решающим и что ты отклонил/переделал. Не потому что мы не верим логу, а чтобы нам было легче увидеть твою логику. Если ИИ не использовал — так и напиши.
