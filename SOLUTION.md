## API

### Теги поста

| Метод | URL | Тело | Ответ |
|---|---|---|---|
| `POST` | `/api/posts/{post}/tags` | `{"tag_ids": [1,2,3]}` | `200` — пост с тегами |
| `DELETE` | `/api/posts/{post}/tags/{tag}` | — | `204` |

Обе операции требуют аутентификации и авторства поста: аноним получает `401`, чужой
пользователь — `403`, несуществующий пост или тег — `404`, невалидный список — `422`,
превышение частоты — `429` (`throttle:60,1`).

### Справочник тегов

| Метод | URL | Доступ |
|---|---|---|
| `GET` | `/api/tags` | публично, пагинация, `posts_count` у каждого тега, `throttle:120,1` |
| `GET` | `/api/tags/{tag}` | публично |
| `POST` | `/api/tags` | `auth` |
| `PATCH` | `/api/tags/{tag}` | `auth` + `TagPolicy` |
| `DELETE` | `/api/tags/{tag}` | `auth` + `TagPolicy` |

```bash
curl http://localhost:8000/api/tags
curl http://localhost:8000/api/posts/1
```

**Важное ограничение окружения.** Изменяющие операции по реальному HTTP недостижимы, и это
не неудобство, а следствие того, что в приложении нет транспорта аутентификации: `laravel/sanctum`
не установлен, маршрута логина нет ни одного, а группа middleware `api` в Laravel 11 при пустом
`withMiddleware()` состоит ровно из одного `SubstituteBindings` — без `StartSession`. Сессионный
guard `web`, в который резолвится `auth`, физически не может увидеть сессию на этих маршрутах.

Проверено экспериментально на изолированной копии: логин пользователя через web-маршрут
возвращает валидную cookie, та же cookie на web-маршруте даёт 200, а на `/api/posts/{post}/tags`
— 401.

Поведение fail-closed, то есть безопасное, и чинить его правкой `bootstrap/app.php` нельзя:
добавление `StartSession` в группу `api` откроет CSRF, потому что `ValidateCsrfToken` там тоже
отсутствует. Корректное решение — установка Sanctum с токенами, но это выходит за рамки задания,
которое об аутентификации не упоминает. Эндпоинты покрыты feature-тестами
(`tests/Feature/PostTagTest.php`, `tests/Feature/TagTest.php`), где `actingAs()` подставляет
пользователя в guard напрямую.

## Принятые решения

**Хранилище связи.** Таблица `post_tag` с композитным первичным ключом `(post_id, tag_id)`
вместо суррогатного `id`: строка связи идентифицируется парой, а дубль становится невозможен на
уровне БД, а не только на уровне кода. Каскадное удаление с обеих сторон, отдельный индекс на
`tag_id` для обратного направления выборки.

**Идемпотентность.** Привязка использует `syncWithoutDetaching()` — повторный запрос с теми же
тегами не создаёт дублей и не падает. Отвязка тоже идемпотентна: если связи не было, возвращается
`204`, а не `404`. DELETE по семантике HTTP описывает желаемое конечное состояние, а не факт
удаления строки; и пост, и тег при этом существуют — их наличие гарантирует route-model binding.
Это осознанно не то же самое, что «тихо проглотить невалидный ввод»: невалидный ввод как раз
отклоняется явно.

**Коды ответов.** Привязка возвращает `200`, а не `201`: меняется состав связи, новый адресуемый
ресурс не создаётся. Отвязка — `204` без тела, как `destroy` в baseline.

**Валидация.** Вынесена в FormRequest'ы целиком. Ключевое свойство: запрос отклоняется целиком до
любой записи в БД — если в пачке из двух идентификаторов один несуществующий, не запишется ни
один (тест `test_attach_is_rejected_when_any_tag_does_not_exist_and_nothing_is_written`).
Размер пачки ограничен (`max:50`) — прямой урок из `PublishController`.

**Слои.** Привязка и отвязка живут методами на модели `Post`, а не в отдельном сервисе:
`PostTagService` из двух строк был бы слоем ради слоя, Eloquent-связь уже является доменным API.
Контроллер только принимает провалидированный запрос, вызывает модель и отдаёт ресурс.

**Авторизация.** `PostPolicy::manageTags` (автор поста) подключена на уровне маршрута через
`->can()`, поэтому правило видно прямо в списке маршрутов, а контроллер не засорён проверками.

У тегов владельца нет — это общий справочник, — поэтому проверка «свой/чужой» к ним
неприменима. Но одной аутентификации оказалось мало: `post_tag.tag_id` объявлен
`cascadeOnDelete`, и удаление записи справочника вычищает связи у постов всех пользователей.
Получалось, что прямой путь к чужим тегам закрыт политикой, а обходной — через
`DELETE /api/tags/{tag}` — открыт. Поэтому `TagPolicy` ограничивает правку и удаление по
радиусу поражения: менять запись можно, только пока она не стоит на чужих постах.

**Slug.** Генерируется из названия, если не прислан явно; `Str::slug` корректно транслитерирует
кириллицу, но на иероглифах возвращает пустую строку — такой случай отклоняется с понятной
ошибкой, а не создаёт тег с пустым slug. Формат проверяется строгим regex, а не `alpha_dash`
(тот пропускает верхний регистр и unicode). Присланный slug не «чинится» молча: он либо валиден,
либо отклоняется. При переименовании тега slug не пересобирается — он часть публичного адреса.

## Изменения в baseline-файлах

| Файл | Что и зачем |
|---|---|
| `PostController` | `with('user')` → `with('user', 'tags')` в 4 местах. Без этого требование «теги в представлении поста» невыполнимо: `PostResource` отдаёт теги только при загруженной связи. Ни строки логики не переписано. |
| `PostResource` | Заглушка-комментарий заменена на `'tags' => TagResource::collection($this->whenLoaded('tags'))`. |
| `Post`, `Tag` | Добавлены связи и методы привязки/отвязки. |
| `phpunit.xml` | Раскомментированы `DB_CONNECTION=sqlite` и `DB_DATABASE=:memory:`. В baseline они закомментированы, из-за чего тесты с `RefreshDatabase` работали на боевой `database/database.sqlite` и стирали её при каждом прогоне. |
| `DatabaseSeeder` | Добавлены теги и их раскладка по постам, чтобы эндпоинты можно было потрогать сразу после сидов. |

`app/Http/Controllers/PublishController.php` не изменялся.

## Замечено в baseline, но намеренно не исправлено

Это вне рамок задания, фиксирую, что вижу:

1. `routes/api.php:8` — маршрут `/user` использует guard `sanctum`, но `laravel/sanctum` в
   проекте не установлен. Обращение к нему упадёт с «Auth guard [sanctum] is not defined».
2. `PostController::store()` опирается на `auth()->user()`, но на маршрутах постов нет
   middleware `auth` — анонимный `POST /api/posts` даст 500, а не 401.
3. `PostController::update()` и `destroy()` не проверяют авторство: любой аутентифицированный
   пользователь может править и удалять чужие посты. Мои эндпоинты такую проверку делают —
   отсюда расхождение в строгости между baseline и новым кодом.
4. `tests/Feature/PostTest.php:17` — свойство `$this->user` создаётся динамически, в PHP 8.2+
   это deprecated. В своих тестах объявляю свойства явно.
