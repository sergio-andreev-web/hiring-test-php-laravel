## 1. `phpunit.xml` — изоляция тестовой БД

**Что:** раскомментированы две строки:

```xml
<env name="DB_CONNECTION" value="sqlite"/>
<env name="DB_DATABASE" value=":memory:"/>
```

**Зачем:** в baseline они закомментированы, поэтому тесты с `RefreshDatabase` работали не на
отдельной БД, а на рабочей `database/database.sqlite` — и пересоздавали её при каждом прогоне.
Данные там генерируемые (faker + сиды), терять нечего, но тесты при этом не изолированы:
результат прогона зависит от состояния локальной БД, а параллельный запуск невозможен.

**Последствия правки:** тесты гоняются на in-memory SQLite, полностью изолированы друг от друга
и от dev-данных, плюс работают быстрее (нет обращений к файлу). Проверено: после фикса
`php artisan test` оставляет dev-БД нетронутой.

**Почему это важно для оценки:** «изоляция БД между тестами» — прямой пункт критериев в README.

## 2. `database/migrations/2024_01_01_000040_create_post_tag_table.php` — новая таблица связи

**Что:** таблица `post_tag` (имя по конвенции Laravel: singular + алфавитный порядок) с
`post_id`, `tag_id`, `timestamps`.

**Ключевые решения:**

| Решение | Зачем |
|---|---|
| `primary(['post_id','tag_id'])` вместо `id()` | Строка связи идентифицируется парой, суррогатный ключ не нужен. Композитный PK — это одновременно и гарантия уникальности **на уровне БД**, и индекс для выборки тегов поста. Дубль связи физически невозможен, даже если ошибётся код приложения. |
| `constrained()->cascadeOnDelete()` на обеих колонках | Удаление поста или тега не оставляет висячих строк в связи. Без этого в pivot копился бы мусор со ссылками на несуществующие записи. |
| `index('tag_id')` отдельно | Левая колонка композитного PK (`post_id`) обслуживает запрос «теги поста», но не «посты тега». Обратное направление без своего индекса шло бы full scan. |
| `timestamps()` на pivot | Видно, когда тег был привязан. Стоит дёшево, при разборе инцидентов полезно. |

**Проверено тестами:** `test_deleting_a_tag_removes_its_links`, `test_deleting_a_post_removes_its_links`.

## 3. `app/Models/Post.php` — связь и поведение

**Что добавлено:**

- `tags(): BelongsToMany` — связь M:M с `withTimestamps()`.
- `attachTags(array $tagIds): void` — привязка тегов.
- `detachTag(Tag $tag): void` — отвязка.

**Зачем методы на модели, а не сервис:** критерий README — «модель ≠ контроллер», то есть логика
не должна жить в контроллере. Отдельный `PostTagService` на две строки кода был бы лишним слоем
ради слоя: Eloquent-связь и так является доменным API. Поведение живёт в модели, контроллер
остаётся тонким.

**Почему `syncWithoutDetaching`, а не `attach`:** `attach()` при повторной привязке того же тега
попытается вставить дубль и упрётся в композитный PK (ошибка 500 на ровном месте).
`syncWithoutDetaching()` идемпотентен — повторный запрос просто ничего не меняет.

**Почему транзакция:** при нескольких тегах это несколько INSERT-ов. Если один упадёт (например,
тег удалили между валидацией и записью), пост не останется с наполовину применённым набором.
Оговорка честности ради: транзакция даёт атомарность, но не защищает от гонки двух одновременных
запросов — от неё защищает композитный PK на уровне БД.

## 6. `app/Http/Requests/AttachTagsRequest.php` — новый файл

**Что:** валидация входных данных для привязки тегов.

```php
'tag_ids'   => 'required|array|min:1|max:50',
'tag_ids.*' => 'integer|distinct|exists:tags,id',
```

**Зачем именно так:**

- `exists:tags,id` — требование README: каждый идентификатор обязан ссылаться на существующий тег.
- `distinct` — дубли внутри одного запроса это ошибка клиента, а не то, что нужно молча проглотить.
- `max:50` — верхняя граница пачки. Прямой урок из `PublishController`, где `post_ids` не ограничен ничем.
- `messages()` на русском — в стиле baseline (`StorePostRequest`).
- `tagIds()` — типизированный аксессор, чтобы контроллер не разбирал сырой массив руками.

**Главный эффект:** запрос отклоняется целиком **до** любой записи в БД. Если в пачке из двух
идентификаторов один несуществующий — не запишется ни один. Закреплено тестом
`test_attach_is_rejected_when_any_tag_does_not_exist_and_nothing_is_written`.

## 11. `routes/api.php` — два новых маршрута

```php
Route::middleware('auth')->group(function () {
    Route::post('posts/{post}/tags', [PostTagController::class, 'store'])
        ->can('manageTags', 'post');
    Route::delete('posts/{post}/tags/{tag}', [PostTagController::class, 'destroy'])
        ->can('manageTags', 'post');
});
```

**Зачем такие URL:** теги — вложенная коллекция поста. `POST /posts/{post}/tags` добавляет в
коллекцию, `DELETE /posts/{post}/tags/{tag}` убирает конкретный элемент. Это стандартная
REST-конвенция для управления связью.

**Зачем авторизация на уровне маршрута:** правило видно прямо в списке маршрутов, а контроллер
не засоряется проверками. Порядок важен: `auth` отрабатывает первым и даёт анониму 401,
`can` — 403 чужому пользователю.

**Коды ответов:**

- привязка → **200** с постом и его тегами (мы меняем состав связи, а не создаём новый адресуемый ресурс, поэтому не 201);
- отвязка → **204** без тела.

## 12. `app/Http/Controllers/PostController.php` — единственное касание baseline-контроллера

**Что:** `with('user')` → `with('user', 'tags')`, `load('user')` → `load('user', 'tags')`
(4 места: index, show, store, update). Больше ничего не тронуто.

**Зачем:** требование README «теги в представлении поста» иначе невыполнимо — `PostResource`
отдаёт теги только при загруженной связи, а baseline грузил лишь `user`. Правка аддитивная:
ни одной строки логики не переписано.

**Почему во всех четырёх методах, а не только в show:** иначе ключ `tags` был бы в ответе то
есть, то нет — контракт API должен быть одинаковым на всех эндпоинтах поста.

**Почему не через `protected $with = ['tags']` на модели:** глобальный eager-load грузил бы теги
вообще везде, включая `Post::all()` в `PublishController`, то есть менял бы поведение чужого кода.

## 13. `tests/Feature/PostTagTest.php` — новый файл, 16 тестов

Требуется минимум 3 (привязка, отвязка, чтение поста с тегами) — они есть, плюс:

| Группа | Тесты |
|---|---|
| Привязка | один тег; несколько за запрос; повтор не плодит дублей |
| Валидация | несуществующий id → 422 **и пустой pivot**; без `tag_ids` → 422; дубли id → 422 |
| Доступ | аноним → 401; чужой пост, привязка → 403; чужой пост, отвязка → 403 |
| Отвязка | удаляется только нужный тег; отвязка непривязанного идемпотентна; несуществующий тег → 404 |
| Чтение | пост отдаётся с тегами (структура + состав) |
| Производительность | список постов не даёт N+1 (счётчик запросов) |
| Целостность | удаление тега и удаление поста чистят связь |

**Про тест на N+1:** считаю запросы через `DB::enableQueryLog()`. Просилось `Model::preventLazyLoading()`,
но Laravel не сбрасывает этот статический флаг между тестами — он протёк бы в соседние тесты,
где ленивая загрузка легальна. Счётчик запросов даёт тот же результат без глобальных побочек.

**Мелочь по стилю:** свойства `$user`/`$post` объявлены явно. В baseline `PostTest` они создаются
динамически — в PHP 8.2+ это deprecated.

# Опциональное расширение — CRUD справочника `/tags`

README помечает его как «приветствуется, но не требуется». Сделан полностью.

## 14. `app/Http/Controllers/TagController.php` — новый файл

**Что:** `index`, `show`, `store`, `update`, `destroy`.

**Решения:**

- `index` — пагинация `paginate(15)`, как в `PostController`. Отдавать справочник целиком
  нельзя: он растёт без ограничений.
- `withCount('posts')` — количество постов у тега считается одним запросом на всю страницу.
  Наивный `$tag->posts()->count()` в цикле дал бы N+1 (ровно то, за что критикуется
  `PublishController`).
- `destroy` — связи в `post_tag` убирает каскад на уровне БД, вручную чистить не нужно.

## 15. `StoreTagRequest` / `UpdateTagRequest` — новые файлы

**Автогенерация slug (`prepareForValidation` в Store):** если `slug` не прислали, он строится из
названия. `Str::slug()` корректно транслитерирует кириллицу (`Чистый Код` → `cistyi-kod`), но на
иероглифах или строке из одной пунктуации возвращает **пустую строку**. Поэтому пустой результат
намеренно не подставляется — срабатывает правило `required`, и клиент получает понятную ошибку
вместо тега с пустым slug.

**Формат slug — строгий regex `^[a-z0-9]+(?:-[a-z0-9]+)*$`,** а не `alpha_dash`:

- `alpha_dash` пропускает верхний регистр, подчёркивания и unicode-буквы, то есть в БД попали бы
  `My_Slug` и кириллические slug-и;
- «починить» невалидный slug молча через `Str::slug()` — плохой вариант: это тихая подмена
  пользовательского ввода. Присланный slug либо валиден, либо отклоняется с 422.

**Slug не пересобирается при переименовании (`UpdateTagRequest`):** slug — часть публичного
адреса тега. Менять его автоматически при правке названия значит ломать внешние ссылки.
Нужно сменить — пришли `slug` явно.

**Уникальность при обновлении:** `Rule::unique('tags','slug')->ignore($this->route('tag'))` —
без `ignore` тег не смог бы сохранить собственный slug.

## 16. `app/Http/Resources/TagResource.php` — дополнен

Добавлен `'posts_count' => $this->whenCounted('posts')` — поле появляется только там, где
счётчик действительно посчитан, и не провоцирует лишних запросов.

## 18. `tests/Feature/TagTest.php` — новый файл, 17 тестов

валидный латинский slug по нашему же regex), а не таблицу транслитерации библиотеки, которая
является деталью реализации и может поменяться с версией.

# Правки по итогам security-аудита

Полный аудит (скиллы Trail of Bits, Anthropic и netresearch + Semgrep) дал 159 находок.
В коде Блока А — пять. Ниже что исправлено и почему.

## 19. `app/Policies/TagPolicy.php` — новый файл. Закрыта дыра в авторизации

**Что было:** `/api/posts/{post}/tags` защищён `PostPolicy::manageTags` и корректно отдаёт 403
чужому. Но `TagController::update/destroy` стоял только под `auth`, без политики, а
`post_tag.tag_id` объявлен `cascadeOnDelete()`. Посторонний удалял тег — каскад вычищал связи
у постов **всех** пользователей. Прямой путь закрыт, обходной открыт.

**Ошибка в рассуждении:** я решил, что раз у тега нет владельца, достаточно аутентификации.
Про владельца верно, но не учтён радиус поражения: удаление записи общего справочника меняет
данные чужих пользователей.

**Как исправлено:** `TagPolicy::update/delete` разрешают операцию, только если тег не стоит ни
на одном чужом посте. Свой или ничей тег правится и удаляется свободно, общий — нет.
Подключено на маршрутах через `->can('update', 'tag')` и `->can('delete', 'tag')`.

## 20. `Post::attachTags()` — гонка и линейный рост запросов

**Гонка:** `syncWithoutDetaching` это read-then-write без блокировки. Два одновременных запроса
с одним тегом оба видели «связи нет» и оба пытались вставить. Составной PK не давал появиться
дублю, но проигравший получал 500. Воспроизведено PoC в ходе аудита.
Исправлено перехватом `UniqueConstraintViolationException`: нужное состояние уже достигнуто,
поэтому исключение поглощается, и операция идемпотентна и под конкурентной нагрузкой.

**Запросы:** `syncWithoutDetaching` внутри вызывает `attach()` отдельно на каждый тег — пачка
из 20 тегов давала 20 INSERT-ов. Заменено на выборку уже привязанных плюс одну вставку
недостающих: два запроса независимо от размера пачки.

**Комментарий в коде переписан** — прежняя формулировка заявляла идемпотентность без оговорки
про конкурентность, то есть вводила в заблуждение.

## 21. `AttachTagsRequest` — валидация перестала масштабироваться

Правило `exists:tags,id` на элементах массива выполняет отдельный SELECT на каждый
идентификатор: 50 тегов — 50 запросов только на проверку. Заменено на один `whereIn` в
`withValidator()`. Формат ошибок сохранён прежний (`tag_ids.0`, `tag_ids.1` …), чтобы контракт
API не изменился.

Ирония находки: ограничение размера пачки мы сделали, помня урок `PublishController`, а
собственный N+1 в валидации не заметили.

## 22. `StoreTagRequest` / `UpdateTagRequest` — модификатор `D` в regex

Без него метасимвол `$` совпадает и перед завершающим переводом строки, поэтому `"laravel\n"`
проходил валидацию. На практике это гасил глобальный `TrimStrings`, то есть правило держалось
за счёт чужого middleware. Добавлен `D` — правило защищает себя само.

## 24. Rate limiting и недостающие тесты на 404

**Что:** все маршруты Блока А переведены под `throttle`. Изменяющие операции — `throttle:60,1`,
публичное чтение справочника — `throttle:120,1`.

**Зачем:** в Laravel 11 ограничение частоты для группы `api` не включается само — нужен вызов
`throttleApi()` в `bootstrap/app.php`, которого в baseline нет. Без него любая ошибка
авторизации масштабируется циклом, а привязка тегов это запись в БД. Использован inline-лимит
(`throttle:60,1`), а не именованный: именованный потребовал бы регистрации `RateLimiter::for()`
в провайдере, то есть правки файла, к задаче не относящегося.

**Тесты:** добавлены три — 404 при привязке к несуществующему посту, 404 при отвязке от
несуществующего поста и проверка, что ни один маршрут тегов не остался без `throttle`.
